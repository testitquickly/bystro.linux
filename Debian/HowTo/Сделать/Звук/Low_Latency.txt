====== Low Latency ======

[ @debian @sound @real-time ]

Есть мнение о том, что записывать звук надо в специализированные устройства, а в ноутбуке его только редактировать, но это обсуждаемо.

В норме, чтобы эффективно записывать и редактировать музыку «на компьютере», надо использовать ядро Linux с низкой задержкой — real‑time, оно же “rt”. Ядро real‑time не обязательно гарантирует максимально низкую задержку, но оно даёт реальные преимущества для работы с аудиозаписью по сравнению со стандартными настройками Debian. Надо установить мета-пакет //linux-image-rt-amd64// и придётся несколько раз перезагружать ноут. См. инструкцию для [[+Debian 12]]

Но в Debian 13 ситуация поменялась, тут звуком уже полностью заведует PipeWire, который не заменяет low-latency kernel, но уже рассчитан на low-latency работу и умеет динамически менять размер буфера обмена. А переход на другое ядро потенциально нарушит устойчивость системы. Поэтому сперва надо проверить  и настроить PipeWire/JACK и realtime-приоритеты, а уже затем решать, действительно ли нужно ставить отдельное ядро linux-image-...-rt или low-latency kernel. 

===== Проверить текущий стек =====

В норме pipewire.service и wireplumber.service должны быть загружены и стабильны.

''systemctl --user status pipewire wireplumber''

===== Поставить JACK-совместимость PipeWire =====

Если есть ПО, которое работает через JACK:

''sudo apt install pipewire-jack''

Также можно поставить alsa-utils:

''sudo apt install alsa-utils''

===== Проверить realtime =====

В Debian для этого есть RTKit (rtkit) — демон, который позволяет обычным пользовательским процессам получать SCHED_RR realtime-планирование.

Проверить:

''systemctl status rtkit-daemon''

Ожидаем состояние Active: active (running). Сервис может быть disabled — это нормально, его будем вызывать при необходимости. 

Если его нет:

''sudo apt install rtkit''

===== Проверить интерактивный монитор PipeWire =====

Это примерно аналог утилиты //top// для аудиостека:

''pw-top''

Откроется интерактивная (постоянно обновляется, ничего не скопируешь) таблица с параметрами работающих аудиопроцессов.

Если запись будем делать через [[Software:Audacity]] — включить в нем что-то и вызвать pw-top. Смотреть на строку этого процесса. Заголовки таблицы подсказывают:

''QUANT  RATE''
''384   48000''

* QUANT = 384 — PipeWire обрабатывает аудио блоками по 384 сэмпла. Исходно 1024.
* RATE = 48 000 сэмплов в секунду.

Размер одного такого блока:

''384 / 48000 = 0,008 с = 8 мс''

То есть quantum = 384 даёт 8 мс на обработку одного аудиоблока (буфер), который PipeWire обрабатывает за один цикл.

Это не обязательно полная round-trip latency от входа звуковой карты до выхода. Реальная задержка записи/мониторинга может быть больше из-за входного/выходного буферов, устройства и обработки.

Для записи музыки эти параметры надо постепенно уменьшать:

''1024 → 512 → 256 → 128 → 64''

…пока не доходишь до пределов стабильности, которые смотрим в таблице //pw-top// в колонке //ERR.// В норме там ''0''. Если буфер будет слишком низким и аудиосистема перестанет успевать вовремя обработать очередной блок аудиоданных, вместо нуля появятся какие-то цифры. 

Есть два варианта:

* Underrun — программе/выходному устройству нечего проигрывать вовремя → появляются щелчки, провалы, заикания.
* Overrun — входные данные пришли, а система не успела их обработать → часть записываемого звука может потеряться.

Это срыв realtime-аудиопотока, и обычно это называют «XRUN». Если они появляются, значит надо вернуться к большим значениям в настройке. 

При настройке low latency надо найти минимальный QUANT, при котором система длительно работает без XRUNs. Планируем  добиться стабильных:

* 48 kHz
* 128 samples

или даже:

* 48 kHz
* 64 samples

без xruns. 

===== Настроить низкую задержку =====

Изначально аудиосистема работает в автоматическом режиме.

Включить воспроизведение звука. 

Открыть два терминала.

Проверить текущие настройки:

''pw-metadata -n settings''

Пример ответа:

''Found "settings" metadata 32''
''update: id:0 key:'log.level' value:'2' type:''''
''update: id:0 key:'clock.rate' value:'48000' type:''''
''update: id:0 key:'clock.allowed-rates' value:'[ 48000 ]' type:''''
''update: id:0 key:'clock.quantum' value:'1024' type:''''
''update: id:0 key:'clock.min-quantum' value:'32' type:''''
''update: id:0 key:'clock.max-quantum' value:'2048' type:''''
''update: id:0 key:'clock.force-quantum' value:'0' type:''''
''update: id:0 key:'clock.force-rate' value:'0' type:''''

Ок, ''clock.quantum' value:'1024''. 

В первом терминале запустить pw-top. Смотрим на QUANT для устройства, через которое система воспроизводит звук (ноутбук или внешняя аудиокарта) — там QUANT покажет какое-то значение, например, **512**.

Во втором терминале задать размер аудиобуфера PipeWire в 128 сэмплов при действующей настройке 48 кГц:

''pw-metadata -n settings 0 clock.force-quantum 128''

В первом терминале смотрим на QUANT для устройства, через которое система воспроизводит звук (ноутбук или внешняя аудиокарта) — там QUANT должен измениться на **128**.

Если что-то пойдёт не так — вернуть автоматический режим:

''pw-metadata -n settings 0 clock.force-quantum 0''

Считаем:

''128 / 48000 = 2,67 мс''

То есть один аудиоблок обрабатывается каждые примерно 2,67 мс. Для записи электрогитары это прям отлично.

Учесть, что наушники для записи должны быть проводными. BlueTooth принесёт свою дополнительную задержку, особенно если включить для них воспроизведение высокого качества.
